## 2. 毎回の進め方（ユーザーとの約束）

> **2026-11-05 にユーザーが決めた約束（トークンと待ち時間を減らす。下の 2・6 と「デプロイ前の確認」の 2・5・6 より優先）**
> - **本番への反映は、変更のたびに行う**: 手元では、変えたところに関係するテスト（PHP 単体と、関係する画面テスト数本）だけを流す → 作業ブランチに push → PR を作る → **CI の結果を待たずに、聞かずにマージ**する。本番への反映（`deploy`）は、取り込んだあとの CI のテスト（unit・mariadb・compat・e2e）にすべて通ったときだけ、自動で行われる（落ちたら本番は変わらないので、次の作業で直す）。反映できたかは、終わるころに1回だけ確かめる（または、次の作業のついでに）。
> - **2026-11-10 から、PR の作成とマージは自動**: 作業ブランチに push すると `auto-pr` が PR を作り、PR 側の CI がすべて成功すると `auto-merge` が本番ブランチへマージする。人は push するだけでよい。**手でマージしない**（自動マージと競合するため）。まだ本番に出したくないときは、PR を下書き（Draft）にする。
> - **全部の画面テスト（手元）は、まとめて行う**: 更新が何回か（目安 3回）たまったら、Claude から「全部のテストを流すか」をユーザーに確認する。
> - **金曜日の夕方**は、週の使用量の上限に余裕があるので、ふだんより多く回してよい。
> - 待つときは、こまめに状態を見ない（終わるころに1回だけ確かめる）。
> - **Slack 連携のテストは、本当に必要なとき以外は行わない**（2026-11-09 のユーザーの指示。トークンをかなり使うため）。
>   - 手元で全部の画面テストを流すときは、Slack のテストの `sl`（本物の cron を動かし、次の分まで約1分待つ）を外す: `bash tests/e2e/run.sh $(bash tests/e2e/run.sh --list | tr ' ' '\n' | grep -v -x sl)`。`sl` を流すのは、Slack の通知・送り先・時刻指定のテスト送信・cron（`src/slack.php`・`bin/cron.php`・`notify_*`）を変えたときだけ。
>   - 本番の Slack に、確かめのためのテスト送信（「テスト通知を送る」「時刻を指定してテスト送信」）を頼んだり、届くのを待ったりしない。ユーザーが自分で試したいときだけ。
>   - GitHub の CI は、これまでどおり全部のテスト（`sl` を含む）を流す（Claude のトークンは使わない）。

1. 実装する。
2. 確かめる: PHP 単体テスト（SQLite と MariaDB）、画面テスト（Playwright）。必要なら古い DB からのアップグレードも。
3. `src/version.php` の `APP_VERSION` を上げる。
4. コミット（メッセージの末尾に、指定のトレーラーを付ける）して、ブランチに push する。
5. 返事は日本語で、「**変えたこと／確かめたこと／確かめていないこと**」の3つを書く。
6. **push すると、PR の自動作成（`auto-pr`）→ CI 成功後の自動マージ（`auto-merge`）が行われる。手でマージしない。** 取り込んだあとの `deploy` ジョブの成功まで確かめる（ユーザーの約束。どのアプリでも共通）。CI が落ちたら、直して push する（自動マージは、成功したときだけ行われる）。
7. 本番に反映できたら、ユーザーに実機確認を頼む。

### デプロイ前の確認（必須。2026-10-22 にユーザーが決めた約束）

機能を足したり直したりするたびに、**他の部分にエラーが出ていないことを確かめてから**、本番に出す（デプロイ対象のブランチに取り込む）。

1. **影響範囲を洗い出す**: 変えた関数・CSS・API・画面を `grep` で探し、ほかの使い方（業務版・プライベート版・共有ページ（会社用／家族用）・家族のアカウント・スマホ幅・ダークモード・リスト表示）を確かめる。1つの画面だけ直して、同じ部品を使う別の画面を忘れない（例: v1.80.0 の「休みだけ」は、共有ページで効かなかった）。
2. **テストは、選んだ数本ではなく、すべて流す**: `php tests/run.php`（SQLite）と `bash tests/e2e/run.sh`（全部）。`E2E_SHOW=1` を付けて流し、`PAGEERR`（画面のJSエラー）が出ていないかも見る。MariaDB はこの環境に無いので、CI の `mariadb` で確認し、確認前は「確かめていない」と書く。
3. **既存のテストが落ちたら、テストを飛ばしたり弱めたりしない**: 仕様を変えたせいなら、仕様に合わせて直す（理由を書く）。不具合なら、コードを直す。
4. **新しい動きには、新しいテストを足す**（既存の動きを壊していないことは、全部のテストで確かめる）。
5. **取り込む前に、その版の CI（PR 側）がすべて成功していること**を確かめる。実行中なら、終わるまで待つ。成功したら、ユーザーに聞かずに取り込む（PR → マージは一続き）。
6. **取り込んだあとも、`deploy` ジョブの成功まで確かめる**。失敗したら、ログで原因を調べる。同じコードの別の実行が成功していて、ドラッグ操作などの時々落ちるテストだと言えるときだけ、失敗したジョブを1回だけやり直す。2回目も落ちたら、本物の不具合として直す。
7. 返事の「確かめたこと／確かめていないこと」には、上の何をやって、何をやっていないかを、ごまかさずに書く。

ユーザーがパスワードや鍵をチャットに貼らないこと（Secrets は GitHub の設定画面だけ）。認証情報をコミットしない。

## 3. 自動デプロイ（GitHub Actions）

- `.github/workflows/test.yml`。ブランチに push すると、unit（PHP 7.4/8.1/8.3）・mariadb・compat・e2e が走り、**すべて通ったときだけ** `deploy` ジョブが FTPS でサーバーに反映する。
- `.github/workflows/auto-pr.yml`。作業ブランチ（`claude/**`）へ push すると、本番ブランチ向けの PR を自動で作る（同じ組み合わせの PR があれば作らない）。
- `.github/workflows/auto-merge.yml`。作業ブランチの `tests`（**push 側**）がすべて成功したら、そのブランチの PR を本番ブランチへ自動でマージする（下書きの PR と、テストしたコミットより新しい push がある PR は、その回はマージしない）。マージ後は `workflow_dispatch` で本番ブランチの `tests`（`deploy` を含む）を始める。
  - `auto-pr` が `GITHUB_TOKEN` で作った PR は、**PR 側**のテスト実行が「承認待ち（`action_required`）」になり、ジョブが動かないことがある。そのため、同じコミットの push 側の成功で判断している。PR の画面に承認待ちが残っても、マージは行われる。
  - **`GITHUB_TOKEN` でマージすると、その push ではワークフローが動かない**（GitHub の仕様）。そのため、マージ後の本番ブランチのテストと反映は、`auto-merge` が `gh workflow run tests --ref <本番ブランチ>` で明示的に始める。`test.yml` は `workflow_dispatch` を受け付け、`deploy` は「本番ブランチへの push」か「本番ブランチを指定した `workflow_dispatch`」のときだけ動く。
- 自動 PR には、リポジトリの Settings → Actions → General → Workflow permissions の「Allow GitHub Actions to create and approve pull requests」が必要（2026-11-10 に有効化ずみ。`can_approve_pull_request_reviews: true`）。ブランチ保護はしていない。
- 使うのは SamKirkland/FTP-Deploy-Action（v4.3.5 のコミットで固定）。接続先はワークフローの `sv10007.star.ne.jp` で、`security: strict`（証明書を確かめる。`ss912764.stars.ne.jp` は証明書が一致しない）。Secrets は `FTP_USERNAME` `FTP_PASSWORD` `FTP_SERVER_DIR`（ユーザーが登録済み。`FTP_SERVER` は使わなくなった）。
- `FTP_SERVER_DIR` は **public の親フォルダ**: `/skym.ink/public_html/schedule-management.skym.ink/`。末尾の `/` はワークフローが補う。`/public/` で終わる指定は、ガードが止める。
- 反映するのは一番上の `.htaccess` と `public/ src/ sql/ bin/`（`tools/stage_deploy.py stage`）。除外: `install.php` `app_path.php` そのほかのドットファイル `config.php`。一番上の `.htaccess` は v1.96.1 から反映する（SSL 証明書の更新の経路 `/.well-known/acme-challenge/` を通すため。**反映から外すとサーバーからも消えて `config.php` が見えるので、外さない**）。`deploy` ジョブが、反映のあとに中のファイルが見えないことを確かめる。
- サーバーの `.ftp-deploy-sync-state-schedule.json` は消さない。ローカルで消したファイルは、サーバーからも消える。
- この作業環境からは、FTP も本番サイトも見えない（HTTPS のプロキシのみ）。Secrets の読み書きもできない。本番の確認はユーザーに頼む。
- zip でのシステム更新は、v1.77.0 で廃止済み（`update.php` `updater.php` を削除）。

## 4. 技術メモ

- PHP 7.4 以上（PDO: SQLite / MariaDB）。`SCHEMA_VERSION` は 34。
- フロントは `public/assets/app.js` 1本（ES5 の IIFE。**アロー関数・テンプレートリテラルは使わない**）。補助関数: `el()` `api()` `store()`（localStorage に JSON）`openModal`。設定ページへの埋め込みは `embedHost`。
- 画面の色はテーマ用の CSS トークン。ライト／ダーク／自動はアイコンで切り替え（`themeSwitch()`）。
- 設定の各項目は、クリックで開閉（状態は `store('sched.setOpen')`）。
- カレンダー: 月表示は4段、週表示は12段まで。あふれると「他 n件」。完了した予定は下に出る。
- ToDo の状態は `todos.doing`（0 未着手 / 1 進行中 / 2 保留）。
- 共有リンクは `share_links`（`created_by` あり）。共有ページで、リンクを作った本人だけに「← 自分の画面に戻る」を出す（サーバーは `mine` の true/false だけ返す）。

### 家族のアカウント（v1.76.x）

- 持ち主（社員）が家族を招待する。`users.role = 'family'`、`users.family_of` に持ち主の番号。1人の持ち主につき最大5人（`FAMILY_MAX`）。
- 家族が使える API は `FAMILY_ALLOWED_ACTIONS` だけ（それ以外は 403）。家族の予定は、常にプライベート／家族共有になる。
- 家族に見えるのは、持ち主の家族用リンクに見える予定と、持ち主の家族の予定。実装は `src/family.php` と、`src/events.php` の分岐。
- 家族は、ユーザー一覧・利用状況・監査ログ・家族の更新履歴には出ない。

### v1.78.0 で入れたもの

- 新しい業務の予定の分類の初期値は「個人作業」（休み→業務の切替時も）。繰り返し業務の登録だけは「定例業務」のまま。
- 開始時刻を入れると、終了時刻に30分後が自動で入る（23:30 以降は 23:59）。手で入れた終了は変えない。自動で入れた終了は、開始を消すといっしょに消える。

### v1.79.0 で入れたもの（日報の自動反映）

- スケジュールに入っている**業務のToDo**（未完了）を、日報に自動で入れる（`memoAutoSync()`、`public/assets/app.js`）。
  - 進行中: 当日の項目へ。カレンダーに先の日付で置いてあるものは、その日付の日報へ（当日より先なら、置いた日が次回出勤日のときだけ次回出勤日の項目へ。それより遠い日は、まだ入れない）。
  - 未着手: 日付が決まっているものだけ、その日付の日報へ。日付 = カレンダーに置いた日（`sched`〜`sched_end`）。置いていなければ期限日。
  - 保留は入れない。完了は、これまでどおり `memoAddDone`（完了にした瞬間に、取り消し線つきで入る）。プライベートのToDoは入れない。
  - 一度入れた（または、すでに日報にある）ToDoは、**当日の見出しの `data-auto`**（「番号:日付」のカンマ区切り、最大40件）に控える。日報から消した行は、入れ直さない。日報に同じ文言の行があれば、足さない。
  - 起動のきっかけ: 日報を開いたとき（`memoReconcile` の中）、ToDoを読み込み直したとき（`syncMemoTodos`）。
- サーバー: `todo_with_event_dates()` が `sched_end`（置いた予定の最終日）も返す。`sanitize_memo_html()` が見出しの `data-auto` を通す（数字・`:`・`-`・`,` だけ、900文字まで）。雛形には `data-auto` を持ち込まない。
- 画面テスト `memoauto`（新規）。
- **ユーザーに確かめてもらうこと**: 「スケジュール」の意味を、「カレンダーに置いた／日付のあるToDo」と受け取った（カレンダーだけに直接入れた予定は、ToDoと結びついていなければ入らない）。進行中で日付のないToDoも、当日に入れる。意図と違えば直す。

### v1.85.0 で入れたもの（休みの出し方）

- 自分の休みの日を、帯ではなく日付の横の「休」のアイコン（`.offmark`。半休は「半休」）だけで出せる。設定の「休みの出し方」で、業務版とプライベート版で別々に選ぶ（`users.prefs` の `offmark` = `{team, me}`、値は `bar` / `icon`。API `offmark_save`、`save_offmark_pref()`）。**初期値: 業務版 = 帯、プライベート版 = アイコン**（ユーザーの希望）。
- 業務版でアイコンにしても、アイコンになるのは自分の休みだけ（ほかの人の休みは帯）。家族用リンク（`SCHEDULE_SHARE.offmark`）と家族の画面（`me` の `family_owner_offmark`）は、持ち主のプライベート版の設定に従う。会社用リンクは、いつも帯。家族のアカウントは変えられない（403）。
